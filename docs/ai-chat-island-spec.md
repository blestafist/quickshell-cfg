# ТЗ: AI-чат островок (левый остров с Nix-иконкой)

Статус: план согласован, реализация НЕ начата.
Дата: 2026-09-12

## Цель

Превратить левый островок бара (тот, что с иконкой Nix) в раскрывающийся вниз
динамический чат с ИИ, работающий через `opencode` (CLI/сервер), по образу и
подобию WifiPanel/VpnPanel/PowerPanel (внешний вид, анимации раскрытия вниз,
динамическая высота/ширина по контенту).

Открывается по ПКМ на иконке Nix. ЛКМ — поведение не менять (остаётся
открытие лончера, как сейчас).

## Ключевые требования (от пользователя, зафиксировано как есть)

1. Внешний вид и анимации — как у WifiPanel/конфигуратора Wi-Fi: остров
   раскрывается вниз, динамически меняет размер, скруглённые Shape-контуры
   в стиле текущего бара (см. `modules/bar/Bar.qml`, `WifiPanel.qml`).
2. Открытие по ПКМ на Nix-иконке (`leftCluster` в `Bar.qml`).
3. Чат с ИИ через `opencode` (есть headless `opencode serve`, REST+SSE API).
4. Два режима: **Chat** (без тулов, обычный чатбот) и **Agent** (с тулами:
   bash/edit/read/etc, полноценный агент). Переключатель режима в UI.
5. Поддержка сессий: создание, список, переключение, удаление, (желательно)
   fork.
6. **Несколько сессий/агентов одновременно** — несколько вкладок внутри
   острова, каждая вкладка — отдельная сессия opencode, может работать в
   фоне (агент продолжает выполнять тулы), пока открыта другая вкладка.
   Переключение между вкладками — горячей клавишей/комбинацией (уточнить
   удобную комбинацию на этапе реализации, например Ctrl+Tab / Alt+1..9)
   и кликом по табам в UI.
7. Настройки: выбор модели (и провайдера), выбор агента, политика разрешений
   (permissions: спрашивать / авто-разрешать), рабочая директория агента.
8. Вставка картинок в сообщение:
   - из буфера обмена (Ctrl+V, через `wl-paste`);
   - через файловый диалог (выбор файла с диска).
9. Permissions: поддержать оба варианта —
   - всплывающий prompt внутри острова (Allow / Allow Always / Deny), когда
     агент просит разрешение на тул (bash, edit, etc.) и политика = "спрашивать";
   - настраиваемый auto-approve в настройках (политика = "не спрашивать",
     либо потул-детальная настройка, если будет время).
10. Стриминг ответа — живой, через SSE (`GET /event`), как в TUI/курсоре —
    текст должен печататься по кускам, а не появляться целиком после ожидания.

## Рабочая директория агента

По умолчанию — домашняя директория пользователя (`$HOME`), НЕ
`~/.config/quickshell`. Режим по умолчанию при открытии — **Chat** (не
агент), чтобы не путать пользователя лишними тулами сразу.

Директорию для конкретной сессии можно будет сменить в настройках/сессии
(желательно, но не блокер для MVP).

## Исследованный API opencode (зафиксировано для реализации)

### Запуск сервера

- Свой процесс: `opencode serve --port 0 --hostname 127.0.0.1` — порт 0
  означает "выбрать свободный", реальный порт парсится из stdout:
  `opencode server listening on http://127.0.0.1:<PORT>`.
- Предупреждение `OPENCODE_SERVER_PASSWORD is not set; server is unsecured.`
  — ок, сервер слушает только на 127.0.0.1, не страшно для локального шелла.
- Сервис должен сам поднимать `opencode serve` при старте шелла (одним
  инстансом, общим для всех вкладок/сессий чата), и аккуратно завершать
  процесс при `Quickshell.reload()`/выходе, чтобы не плодить зомби-процессы
  при множественных релоадах конфига. Нужна защита от повторного запуска.

### REST (через `curl` процессы, см. заметки ниже)

- `GET /global/health` → `{healthy, version}` — проверка готовности.
- `GET /agent` → список агентов. В текущей установке доступны как минимум:
  `orchestrator`, `Chat` (zero-tool, permission "*": deny — это и есть
  режим "Chat"), `Learn`, `build` (дефолтный агент с тулами — режим
  "Agent"), `plan`, `explore`, `general`, `review`, `slave`, `summary`,
  `title`, `compaction`. Для переключателя Chat/Agent в UI рекомендуется
  взять `Chat` и `build` как базовые два режима (plus возможность выбрать
  кастомный агент из списка в настройках, если юзер захочет).
- `GET /config/providers` → `{providers: Provider[], default}` — список
  провайдеров/моделей (большой JSON, `models.dev`-формат). Есть поле
  `capabilities.attachment` / `capabilities.input.image` — можно
  фильтровать модели по поддержке картинок, если нужно блокировать
  вложение для моделей без image-инпута.
- `GET /provider` → `{all, default, connected: string[]}` — чтобы понять,
  какие провайдеры реально подключены (авторизованы), и не показывать в
  UI недоступные.
- `POST /session` body `{parentID?, title?}` → создаёт сессию, возвращает
  `Session` объект (`id`, `slug`, `directory`, `title`, ...).
- `GET /session` → список сессий. `GET /session/:id` → детали.
  `DELETE /session/:id` → удалить. `PATCH /session/:id` body `{title?}`.
  `POST /session/:id/fork` body `{messageID?}`.
  `POST /session/:id/abort` → прервать текущий запрос агента.
- `GET /session/:id/message?limit=` → история сообщений
  `{info: Message, parts: Part[]}[]`.
- `POST /session/:id/message` body
  `{messageID?, model?, agent?, noReply?, system?, tools?, parts}` —
  БЛОКИРУЮЩИЙ запрос, ждёт полного ответа модели (проверено: ответ приходит
  целиком после завершения генерации). **Не использовать для живого
  стрима** — вместо этого:
- `POST /session/:id/prompt_async` — тот же body, ответ `204 No Content`
  сразу, а реальный прогресс идёт через `/event` SSE. Это должен быть
  основной способ отправки сообщений в чате.
- `POST /session/:id/shell` body `{agent, model?, command}` — запуск шелл-
  команды от имени агента (не обязателен для MVP).
- `POST /session/:id/permissions/:permissionID` body
  `{response, remember?}` — ответ на permission prompt (`response`:
  предположительно `allow`/`deny`, `remember`: bool для "always"; нужно
  проверить точные значения по `/doc` OpenAPI или по факту первого
  реального permission-события, т.к. в тестовом окружении агент пока не
  просил разрешений — политика была auto-allow).
- `model` в body сообщения — формат `{providerID, modelID}` по аналогии с
  тем что видно в `message.info.model`.
- Вложения (картинки): формат part для файла/изображения нужно уточнить по
  `GET /doc` (OpenAPI spec) на этапе реализации — в документации сервера
  упомянуты части типа `file`, но точная схема (base64 vs URL vs путь)
  не проверена вживую. Первый шаг реализации вложений — дёрнуть
  `GET http://127.0.0.1:<port>/doc` и посмотреть схему `Part`/`FilePart`.

### SSE (`GET /event`)

- Один общий поток на все сессии процесса. Формат: `data: {...}\n\n`
  (классический SSE, без `event:` поля, только `data:`).
- Нужно фильтровать по `properties.sessionID`, чтобы роутить в нужную
  вкладку/модель сообщений.
- Полезные типы событий, подтверждённые вживую:
  - `server.connected` — первое событие после коннекта.
  - `session.updated` — метаданные сессии изменились (cost, tokens, title).
  - `session.status` — `{sessionID, status: {type: "busy"|"idle"}}` —
    индикатор "агент печатает/работает".
  - `message.updated` — `{sessionID, info: Message}` — новое/изменённое
    сообщение (user или assistant), включает `agent`, `model`, `role`,
    `finish` (причина остановки: `stop`, `tool-calls`, ...).
  - `message.part.updated` — `{sessionID, part: Part}` — самое важное для
    стрима: приходит многократно по мере генерации текста и по мере работы
    тулов. Part может быть:
    - `{type: "step-start"}` / `{type: "step-finish", reason}`;
    - `{type: "text", text, time: {start, end}}` — текстовый кусок
      (финальный текст шага, не дельта по символам — проверить, возможно
      нужно аккумулировать по `id` части, апдейты переписывают весь текст
      части, а не добавляют дельту);
    - `{type: "tool", tool: "bash", callID, state: {status: "running"|
      "completed", input: {...}, metadata: {output: "..."}}}` — вызов тула,
      статус меняется running → completed, можно показывать карточку с
      именем тула и выводом.
  - `permission.updated` / `permission.replied` — permission-флоу (тип
    событий предположительный по названию эндпоинта, не наблюдался вживую
    в тестовом окружении — при реализации на это обратить внимание и
    проверить реальные payload'ы, заведя агента на реальное действие с
    политикой "ask").
  - `plugin.added` и прочий шум — игнорировать.
- Технический момент для QML: SSE лучше всего слушать через один
  долгоживущий `Process { command: ["curl", "-sN", "--no-buffer",
  url + "/event"] }` с `SplitParser { splitMarker: "\n\n" }`, который режет
  поток на SSE-фреймы. Проверить на практике, не буферизует ли `curl`
  вывод (добавить `--no-buffer`, возможно `-N` уже достаточно — в тесте
  работало, но тест был синхронный с sleep, не проверяли задержку между
  чанками в реальном времени).

## Архитектура решения

### `services/OpenCode.qml` (новый)

Ответственность:
- Поднять/держать один процесс `opencode serve` (singleton на весь шелл,
  подключается в `shell.qml`, а не в `Bar.qml`, чтобы жил независимо от
  бара и не пересоздавался).
- Держать одно SSE-подключение, диспетчеризовать события по сессиям.
- CRUD сессий, отправка сообщений (`prompt_async`), abort, permissions.
- Кэш списка агентов (`/agent`) и провайдеров/моделей (`/provider`,
  `/config/providers`).
- Модель данных: `sessions: []` — массив объектов вида
  `{ id, title, agent, model, directory, messages: [...], busy, pendingPermission }`
  — то есть **все открытые вкладки/сессии чата живут в этом сервисе**, а не
  в UI-компоненте, чтобы сессии продолжали получать события и работать в
  фоне, даже когда их вкладка не активна/остров закрыт.
- Persist открытых вкладок между перезапусками шелла (список session id +
  какая активна) — через `FileView`/`Quickshell.statePath`, по аналогии с
  `launcher-pins.json`.
- Все REST-запросы — через короткоживущие `Process` с `curl`:
  - GET: `curl -s <url>`.
  - POST с JSON: передавать тело через stdin (`curl -s -X POST url -H
    'Content-Type: application/json' -d @-`) и писать в `action.write(json)`,
    чтобы не светить potentially большие JSON (особенно с base64 картинками)
    в аргументах процесса / списке процессов.
  - Ответы читать через `StdioCollector`, парсить `JSON.parse`.

### Несколько сессий/вкладок (мультисессии)

- UI острова содержит панель вкладок (как табы браузера, компактные,
  горизонтальные, вверху панели чата, под заголовком или вместо него).
- Каждая вкладка = одна opencode-сессия. Можно открыть новую вкладку (+),
  закрыть вкладку (крестик, с подтверждением если агент ещё `busy`),
  переключаться кликом.
- Горячие клавиши переключения вкладок внутри острова (финальную
  комбинацию зафиксировать в `ShellConfig.qml`, по умолчанию предлагается
  `Ctrl+Tab` / `Ctrl+Shift+Tab` для след/пред, и `Alt+1..Alt+9` для прямого
  перехода на вкладку N) — работают только когда остров в фокусе/открыт.
- Вкладка, которая не активна, но у которой `busy: true` (агент работает в
  фоне), должна визуально показывать индикатор (точка/спиннер на табе),
  чтобы было видно, что там что-то происходит, не переключаясь на неё.
- Когда приходит `session.status: idle` для фоновой вкладки — можно мигнуть
  табом / показать бейдж "есть новое сообщение", если вкладка не активна в
  момент завершения ответа.

### `modules/bar/ChatPanel.qml` (новый UI)

Структура (сверху вниз), раскрывается вниз от `leftCluster` аналогично
тому, как `WifiPanel`/`VpnPanel`/`PowerPanel` раскрываются из
`rightCluster` в `Bar.qml`:

1. **Строка вкладок** — список открытых сессий + кнопка "+" новая сессия.
2. **Заголовок активной вкладки** — title сессии (редактируемый?), слева —
   переключатель режима **Chat / Agent** (сегментированная кнопка/тоггл,
   меняет `agent` для следующего сообщения в этой сессии: `Chat` или
   `build`/выбранный кастомный агент), справа — кнопка выбора модели
   (открывает дропдаун со списком provider/model из кэша, с фильтром по
   `connected`), кнопка настроек (шестерёнка), кнопка закрытия острова.
3. **Лента сообщений** — `ListView`, автоскролл к низу при новых частях,
   пока юзер не проскроллил вверх руками (тогда не дёргать скролл).
   - Сообщение юзера — текст + превью прикреплённых картинок.
   - Сообщение ассистента — стримящийся текст (обновляется по
     `message.part.updated`), tool-карточки (компактные, разворачиваемые,
     показывают команду/инпут и вывод, статус running/completed/error
     цветами из темы), индикатор "думает..."/busy для текущего шага.
4. **Permission prompt** (если активен для этой сессии) — плашка над
   инпутом: текст запроса (какой тул/что хочет сделать), три кнопки —
   Allow once / Allow always / Deny. Блокирует отправку новых сообщений до
   ответа (как в TUI).
5. **Превью прикреплённых картинок** (если есть) — чипсы/тумбнейлы над
   полем ввода с крестиком на удаление.
6. **Инпут** — многострочный `TextArea`, Enter = отправить, Shift+Enter =
   новая строка, кнопка "прикрепить картинку" (открывает файловый диалог),
   поддержка `Ctrl+V` вставки картинки из буфера через `wl-paste
   --type image/png` → сохранить временный файл → добавить в список
   вложений (если в буфере текст — вставлять как обычный текст, не ломая
   стандартную вставку текста).
7. **Анимации**: раскрытие вниз такой же высотной анимацией, как
   `rightCluster.targetHeight`/`islandHeightAnimation` в `Bar.qml` —
   `OutBack`/`OutCubic`, длительность ~280-420ms в зависимости от
   направления; динамическая ширина острова по контенту (по аналогии с
   `musicIsland.naturalWidth`), но с разумным максимумом (не шире половины
   экрана) и возможностью пользователю вручную задать/запомнить
   желаемый размер (опционально, не блокер MVP).

### `modules/bar/ChatSettingsPanel.qml` (новый, или секция внутри ChatPanel)

Настройки (скоуп — либо глобальные, либо per-сессия, указать явно в UI):
- Дефолтный агент при создании новой вкладки (Chat/Agent/кастомный).
- Дефолтная модель (провайдер+модель), с fallback на дефолт из
  `/config/providers`.
- Политика permissions: "Спрашивать всегда" / "Авто-разрешать всё"
  (и, если будет время, детальная политика по категориям: bash, edit,
  webfetch, etc — зеркалируя структуру `permission` в ответе `/agent`).
- Рабочая директория для новых сессий (дефолт `$HOME`), с возможностью
  сменить через файловый диалог выбора папки.
- (Опционально, не блокер) список/статус MCP серверов, видно из `GET /mcp`.

### Интеграция в `Bar.qml`

- `leftCluster`: добавить обработку ПКМ на `distroMouse` → toggle
  `aiChatOpened` вместо текущего `launcher.showMessage(...)`.
- ЛКМ на Nix-иконке — не менять (остаётся открытие лончера).
- Нужна height-анимация для `leftCluster` аналогичная `rightCluster`
  (`targetHeight`/`islandHeightAnimation`), т.к. сейчас `leftCluster` умеет
  только расширяться по ширине (`Behavior on width`), вниз не умеет.
  Рекомендуется завести общий механизм (либо скопировать паттерн из
  `rightCluster`, либо выделить переиспользуемый компонент
  `ExpandableIsland.qml` с параметризуемой стороной скругления
  left/right — решение принять на этапе реализации, не блокер для старта).
- `aiChatOpened` добавить в `menuOpened` вместе с
  `wifiOpened || vpnOpened || powerOpened` — при открытии чата остальные
  меню (через правый остров) не обязательно закрывать автоматически (они
  визуально не конфликтуют, т.к. левый и правый остров разные), но нужно
  решить, должен ли чат терять фокус когда открывается, например,
  PowerPanel — вероятно да, по аналогии с текущей логикой в
  `onWifiOpenedChanged` и т.п. (закрывать чат когда открывается что-то
  справа, и наоборот, если это будет визуально пересекаться или мешать
  управлению клавиатурой/фокусом).
- `IpcHandler { target: "aichat" }` — методы: `toggle()`, `close()`,
  `newSession()`, может быть `sendMessage(text)` для внешних интеграций
  (например, быстрый вызов из rofi/скрипта).

## Файлы, которые появятся/изменятся

- `services/OpenCode.qml` — новый. Серверный процесс, SSE-клиент,
  REST-клиент, модель сессий/вкладок, persist state.
- `modules/bar/ChatPanel.qml` — новый. UI чата: вкладки, сообщения, инпут,
  переключатель Chat/Agent, выбор модели, permission-prompt.
- `modules/bar/ChatSettingsPanel.qml` — новый (или секция внутри
  ChatPanel). Настройки.
- `modules/bar/Bar.qml` — правки: `leftCluster` ПКМ-хэндлер, height-
  анимация влево-раскрывающегося острова, подключение `ChatPanel`,
  `IpcHandler { target: "aichat" }`, интеграция `aiChatOpened` в
  `menuOpened`.
- `shell.qml` — подключение `Services.OpenCode` как singleton-инстанса
  (живёт независимо от `Bar.qml`).
- `config/ShellConfig.qml` — добавить константы: дефолтный agent/model,
  горячие клавиши переключения вкладок, дефолтная рабочая директория
  (`$HOME`), ширины/лимиты панели чата.
- `theme/Theme.qml` — возможно добавить цвета для статусов tool-карточек
  (running/success/error), если текущей палитры (`accent`, `danger`,
  `textMuted`) не хватит для наглядности.
- State-файлы через `Quickshell.statePath(...)`:
  `aichat-settings.json` (настройки), `aichat-sessions.json` (список
  открытых вкладок/id активной).

## Открытые вопросы / риски — проверить на старте реализации

1. Точный формат part для картинок/файлов в `POST /session/:id/message` —
   свериться с `GET http://127.0.0.1:<port>/doc` (OpenAPI) перед тем как
   кодить вложения.
2. Точные значения `response` в `POST /session/:id/permissions/:id` и
   реальный payload `permission.*` событий — не наблюдались вживую
   (политика в тестовой среде была auto-allow), нужно спровоцировать
   реальный permission-запрос (например, агент с `permission: {bash: ask}`)
   и посмотреть на реальные события.
3. Поведение `SplitParser`/`curl --no-buffer` на реальном тайминге стрима
   (не протестировано on live partial chunks, только синхронный sleep-тест)
   — проверить что текст действительно появляется построчно, а не разом
   в конце.
4. Наличие `Quickshell.Dialogs`/`FileDialog` модуля в установленной версии
   Quickshell для выбора файла с диска; если недоступен — fallback на
   `zenity --file-selection` / `kdialog --getopenfilename` через `Process`
   (проверить что установлено в системе).
5. Защита от дублирования процесса `opencode serve` при множественных
   `Quickshell.reload()` — нужен явный teardown старого процесса перед
   запуском нового, или переиспользование уже живого процесса, если он
   всё ещё отвечает на `/global/health`.
6. Формат `message.part.updated` для текста — удостовериться, приходит ли
   полный текст части при каждом апдейте (перезапись) или инкрементальная
   дельта — влияет на то, как аккумулировать текст в UI (replace по `id`
   части vs append).
